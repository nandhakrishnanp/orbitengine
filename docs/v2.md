# OrbitEngine — Version 2 Spec

## Problem Statement

Version 1 shipped a working attach-and-fix loop, but the harness is rigid:
the model is hardcoded (`openzen("hy3-free")`), the system prompt and tool set
are fixed for every conversation, and there is no way for a user to shape how
the engine works. In addition, engine activity is not durably persisted —
tool calls and their results (including a produced PR) are only saved when the
client's `onFinish` fires, so work is lost on interruption and is not auditable
as it happens. There is no settings surface, no way to disconnect GitHub, no
browser capability to verify a feature actually works, and no way to teach the
engine reusable behaviour.

## Solution

Give the user control over the harness and make engine work durable and
verifiable:

- **Dynamic model selection** — the user picks the provider and model per
  conversation (with a global default), fetching the live model list from each
  provider. The user provides their own API key per provider in Settings.
- **Modes** — Plan (read-only analysis) and Build (full tool set), switchable
  per conversation.
- **A Settings page** — provider keys, global defaults, loop parameters, and
  GitHub connect/disconnect.
- **Browser capabilities** — `vercel-labs/agent-browser` runs inside the
  conversation's sandbox as an engine tool the model calls to verify a feature.
- **GitHub disconnect** — revoke the app link without destroying history or
  running sandboxes.
- **Durable persistence** — every engine step (tool call + result) is written
  server-side, incrementally, and the `phase` column is populated.
- **Skills** — user-managed Markdown instruction bundles, invoked via
  `/skillname`, addable/editable/deletable in Settings or created from a
  conversation.
- **Observability** — a traces surface showing each conversation's or factory
  run's engine activity: per-step spans (tool, duration, phase, in/out) and
  per-run context (model, provider, skills), read from the durable persistence.
- **Software factory** — a per-repository configuration that polls for new
  issues and autonomously runs the engine to reproduce each one, fix it on a
  branch, and open a PR, monitored from an Ops dashboard.

## User Stories

1. As a developer, I want to choose the model that powers a conversation from
   the chat header, so that I can pick a cheaper or more capable model per task.
2. As a developer, I want to choose the AI provider for a conversation, so that
   I can use whatever model I have access to.
3. As a developer, I want a global default provider and model in Settings, so
   that new conversations start with my preferred model without me choosing each
   time.
4. As a developer, I want to override the model for a single conversation, so
   that one task can use a different model without changing my default.
5. As a developer, I want to add my own API key for each provider in Settings,
   so that the engine can use providers I have accounts with.
6. As a developer, I want the model picker to show only providers I have
   configured a key for, so that I am never offered a provider that will fail.
7. As a developer, I want the model list fetched live from each provider's
   `/models` endpoint, so that newly available models appear without a code
   change.
8. As a developer, I want to store my provider keys securely (encrypted at
   rest), so that my credentials are not stored in plaintext.
9. As a developer, I want to switch a conversation into Plan mode, so that the
   engine only reads repo files and produces an analysis without changing
   anything.
10. As a developer, I want Plan mode to be strictly read-only, so that I can
    safely let the engine explore without risk of writes or pushes.
11. As a developer, I want Plan mode to never run browser verification or other
    write tools, so that analysis is purely observational.
12. As a developer, I want to switch a conversation back to Build mode, so that
    I can let the engine edit code, run tests, and open PRs.
13. As a developer, I want my chosen mode to persist with the conversation, so
    that it is restored when I reopen the conversation.
14. As a developer, I want a Settings page, so that I can manage my account and
    defaults in one place.
15. As a developer, I want to manage provider API keys in Settings, so that I
    can add, update, and remove credentials without editing config.
16. As a developer, I want to set the default mode in Settings, so that new
    conversations start in my preferred posture.
17. As a developer, I want to tune loop parameters (temperature, step cap,
    retries) in Settings, so that I can control cost and behaviour.
18. As a developer, I want to disconnect my GitHub account from Settings, so
    that I can revoke the engine's access to my repos.
19. As a developer, I want disconnecting GitHub to keep my conversation history,
    so that I do not lose my work.
20. As a developer, I want running sandboxes to keep working after I disconnect
    GitHub, so that in-flight work is not abruptly destroyed.
21. As a developer, I want to reconnect GitHub from Settings after
    disconnecting, so that I can resume repo work.
22. As a developer, I want the engine to be able to open a live browser in the
    sandbox, so that it can navigate to a page and verify a feature works.
23. As a developer, I want the engine to decide when to browse, so that it can
    verify a UI or feature as part of its normal workflow.
24. As a developer, I want the browser result (pass/fail, snapshot, page state)
    reported back into the chat, so that I can see the verification.
25. As a developer, I want every engine step (every tool call and its result,
    including a PR URL) saved server-side as it happens, so that work is not
    lost on interruption.
26. As a developer, I want the `phase` of each engine step recorded, so that I
    can see and audit what the engine was doing.
27. As a developer, I want the full engine activity durable even if the client
    disconnects, so that no work disappears.
28. As a developer, I want to create a named skill as a Markdown bundle, so
    that I can teach the engine reusable behaviour.
29. As a developer, I want to add, edit, and delete skills in Settings, so that
    I can maintain my library of reusable instructions.
30. As a developer, I want to invoke a skill by typing `/skillname` in chat, so
    that the engine applies those instructions to the conversation.
31. As a developer, I want my skills available across all my conversations, so
    that I do not recreate them per conversation.
32. As a developer, I want to create a skill from a conversation the engine just
    worked on, so that I can capture a reusable recipe from real work.
33. As a developer, I want to review and edit a skill before it is saved, so
    that the engine never writes a skill to my library without my control.
34. As a developer, I want a skill to be able to declare it needs the browser
    tool, so that a skill can include verification steps.
35. As a developer, I want skills to apply in Build mode only, so that Plan mode
    stays purely observational.
36. As a developer, I want to view the trace of a conversation or factory run, so
    that I can see every step the engine took.
37. As a developer, I want each trace step to show the tool used, its duration,
    and its phase, so that I can see where time went.
38. As a developer, I want each trace to record the model, provider, and skills
    used, plus step count and total duration, so that I understand the context of
    a run.
39. As a developer, I want traces to stream live while a run is active, so that I
    can watch the engine work in real time.
40. As a developer, I want token usage recorded when the provider reports it, so
    that I can track cost per run.
41. As a developer, I want to create a factory for a repository, so that the
    engine watches it for new issues.
42. As a developer, I want a factory to pick up new open issues on its repo and
    run the engine on each one, so that fixes are produced automatically.
43. As a developer, I want a factory run to reproduce the issue in a sandbox, so
    that the fix is verified before a PR is opened.
44. As a developer, I want a factory run to make the fix on a separate branch and
    open a PR, so that I can review and merge like any other PR.
45. As a developer, I want a factory run to open a PR only when it reproduces the
    issue and lands a fix that passes checks, so that unverified changes never
    become PRs.
46. As a developer, I want a run that cannot reproduce/fix the issue to be marked
    failed and to comment on the issue, so that I know what happened.
47. As a developer, I want the factory to skip issues that already have an open
    factory PR, so that I don't get duplicate PRs.
48. As a developer, I want an Ops dashboard with a Factories tab and a Traces tab,
    so that I can monitor runs and inspect traces in one place.
49. As a developer, I want to re-run a failed run from the dashboard, so that I
    can retry after a manual fix without a new issue.
50. As a developer, I want a per-run step/time cap and a concurrency limit, so
    that factory runs stay bounded in cost and runaway behaviour.

## Implementation Decisions

- **Model selection**: add `provider` and `model` columns to the
  `conversations` table (nullable — fall back to the user's global default).
  Add a user-scoped settings store (Postgres) holding the global default
  provider/model, default mode, and loop parameters. The engine route resolves
  the effective provider+model from the conversation's override or the global
  default.
- **Provider registry**: a config-driven registry of OpenAI-compatible
  providers (OpenAI, Anthropic/Claude, DeepSeek, Gemini, opencode.ai). Each
  provider resolves its base URL and a `/models` fetch. The AI SDK
  OpenAI-compatible abstraction (ADR-0010) stays; a provider is available only
  when the current user has a stored key for it.
- **Provider keys**: user-scoped, stored in Postgres, **encrypted at rest**
  (server-side). Keys are managed in Settings (add/update/remove); never sent
  back to the client in plaintext. The picker lists providers whose key the
  user has configured, with models fetched live from `/models`.
- **Modes**: a per-conversation `mode` column (`plan` | `build`), switchable in
  the chat header, defaulting to `build`. The engine tool set is filtered by
  mode: Plan exposes only read tools (read file, list files, read-only command
  inspection); Build exposes the full set plus browser. Writes, PRs, issues,
  repo creation, and browsing are gated out of Plan.
- **Browser capability**: `vercel-labs/agent-browser` runs inside the existing
  conversation sandbox (extending ADR-0004 / one-sandbox-per-loop). Exposed as
  an engine tool the model calls to navigate, interact, and verify a feature;
  the result (snapshot, pass/fail) returns into the chat. Gated to Build mode
  and to skills that declare it.
- **Settings page**: a new route surface for provider keys, global defaults
  (model, mode, loop parameters), and GitHub connect/disconnect.
- **GitHub disconnect**: revoke the GitHub app link for the user (remove the
  NextAuth account link / app installation association). Existing conversations
  and history are retained; running sandboxes continue until closed; repo work
  requires a reconnect. Add a reconnect flow from Settings.
- **Durable persistence (bug fix)**: move persistence server-side and write
  each engine step (tool call + result, including PR URL) to Postgres
  incrementally as it happens, instead of only on client `onFinish`. Populate
  the existing but unused `phase` column with the engine work phase. This makes
  engine activity auditable and interruption-safe.
- **Skills**: a user-scoped `skills` table (name + Markdown content + declared
  tool requirements). Invoked by typing `/skillname` in chat; the engine appends
  the skill's Markdown (and any declared tools, e.g. browser) to its context for
  that conversation. Managed in Settings (add/edit/delete) and via a
  create-from-conversation flow that drafts the skill and asks the user to
  confirm/edit before saving. Skills apply in Build mode only.
- **Observability**: a dedicated trace/step store, written server-side by the
  same loop as the durable persistence (T01). Each engine step becomes a trace
  span — id, runId/conversationId, stepIndex, tool, phase, startedAt, durationMs,
  input, output — plus per-run context (model, provider, skills, stepCount,
  totalMs, and token usage when the provider reports it). Traces stream live via
  SSE. Viewed in the Ops surface; no cross-user metrics in v2.
- **Factory**: a per-repository config that watches for new open issues. Trigger
  is **polling** (Vercel Cron, ~10 min) of the repo's open issues — preserving
  ADR-0002's no-webhook stance — with dedupe via one `factory_runs` row per
  (factory, issue).
- **Factory run**: a dedicated `factory_runs` entity (not a chat conversation)
  that drives the same engine loop, sandbox lifecycle (one sandbox per run,
  ADR-0001), model selection, modes, and trace persistence. Each run reproduces
  the issue in the sandbox, fixes it on a separate branch, runs checks, and opens
  a PR automatically. Opens a PR only when it reproduces AND lands a passing fix;
  otherwise marks the run failed and comments on the issue. Skips issues with an
  open factory PR; no auto-retry (manual re-run from the dashboard); per-run
  step/time caps and a concurrency limit.
- **Ops surface**: a dashboard with a Factories tab (list factories + runs,
  status, re-run/cancel) and a Traces tab (pick a run/conversation → timeline).

## Testing Decisions

- Good tests assert **external behaviour** — the tools the model can call, the
  model/persistence behaviour — not internal implementation. The codebase has
  **no test runner today**, so the first step is to add one (Vitest is the
  natural fit for this Next.js + TypeScript stack).
- The primary **seam** is the engine-loop layer (`lib/engine.ts`, the engine
  route, and persistence in `lib/messages.ts`): test that model selection
  resolves correctly (conversation override vs global default), that Plan mode
  exposes only read tools, that Build exposes the full set, that skill
  invocation injects the skill's Markdown/tools, and that each engine step is
  persisted incrementally with a populated `phase`.
- Test the new modules directly: the provider registry (availability driven by
  configured keys), the settings store (defaults + key encryption round-trip),
  the skills module (add/edit/delete, create-from-conversation draft + confirm),
  the GitHub disconnect path (revoke keeps history; running sandboxes
  unaffected), the trace store (spans + per-run context written correctly), and
  the factory (polling finds new issues, dedupe per issue, run state machine,
  PR-only-on-verified-fix, skip-open-PR, caps/concurrency).
- Prior art: no existing test files, so these are the first; keep tests at the
  module seam and avoid asserting on UI internals.

## Out of Scope

- Agent-driven skill "learning" beyond create-from-conversation (no autonomous
  background skill synthesis).
- Non-OpenAI-compatible providers.
- Browser capability outside the existing sandbox (no separate browser
  sandbox/page).
- Multi-repo conversations (still one repo per conversation, ADR-0007).
- Billing, quotas, or multi-tenant team features.
- Live `/models` caching strategy beyond a short TTL.
- Idle-timeout reclamation of sandboxes.
- Cross-user observability, metrics dashboards, or alerting (traces are
  per-run/per-conversation only in v2).
- Factory webhook triggers (polling only, preserving ADR-0002's no-webhook
  stance), and factory auto-retry (manual re-run only).

## Further Notes

- The provider-key encryption requirement is a security decision that should be
  recorded as an ADR alongside the per-conversation model selection, the skills
  feature, and the browser-in-sandbox integration.
- The factory trigger, run entity, and polling model should be recorded as an
  ADR; observability's trace store as its own ADR.
- The model picker (per-conversation, live `/models`) was already flagged as
  possible without touching the runtime in ADR-0010; this spec realises it.
- Persistence is currently client-driven and completion-only
  (`useChat.onFinish`); moving it server-side is the core fix, and populating
  `phase` restores the intent of the existing column.
